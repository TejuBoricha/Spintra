### 7. How to work here (things that cost time to learn)

- **Workflow:** `AGENTS.md` and `START_HERE.md`: impact assessment before non-trivial changes, `npm run verify`, `npm run test:related`, docs sync (one place per fact), then the change report (compact; the full template for High-risk changes). Every new migration needs a row in `ARCHITECTURE.md` §4 and its "Current status" line; every new doc needs entries in `INDEX.md` and `ARCHITECTURE.md` §2; otherwise the docs-drift check fails.
- **Git in a local session** (the owner's Windows PC, VS Code): the `gh` CLI works and any branch can be pushed; commits end with the session's own `Co-Authored-By` line. **Git in a cloud session:** push only with `git push -u origin claude/loving-noether-1iz9ku:claude/loving-noether-1iz9ku`. After a PR merges, restart the branch with `git checkout -B claude/loving-noether-1iz9ku origin/main` (the push is then a fast-forward because the merge commit contains the old head). Commits end with the `Co-Authored-By` and `Claude-Session` lines; PR bodies end with the "Generated with Claude Code" line; do not put any model identifier in commits, PRs or code. GitHub is reachable only through the `mcp__github__` tools (there is no `gh` CLI).
- **CI:** each pull request head gets one run: `validate` (about 7 to 12 min) and `db-integration` (about 18 to 24 min), plus Vercel Preview Comments; both required checks must be `success` on the exact head, and branch protection also requires the branch to be up to date with `main`. A run tests the merge of the branch into its base. `main` runs again for every push to it; a newer push cancels the older run on the same pull request; a branch without a pull request runs nothing (so never write `[skip ci]`: it would skip the required checks on a pull request head too), and neither does a pull request with merge conflicts (merge `main` into it to get a run); before 10 Oct every push ran everything twice and nothing was cancelled (ADR-013). CI retries a failing test twice, so a flaky pass is green; a cancelled run is not green. Re-run only a job that died before any test ran (runner loss, install hang, port bind), once, with a PR comment saying so; a re-run request returns 403 while the run is still going.
- **Local stack:** Docker, then `npx supabase@2.109.0 start -x studio,logflare,vector,mailpit,imgproxy,postgres-meta,edge-runtime`. Build the app with `NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` taken from `npx supabase@2.109.0 status -o env`, then `next start -p 4000`. Playwright's base URL is `127.0.0.1:4000` (or `PLAYWRIGHT_PORT`), viewport 1280x800; the full suite takes 8 to 9 minutes in the cloud container and about 3 minutes locally (parallel workers). **On the owner's Windows PC:** `.env.local` already points at the local stack; Windows can reserve a block of ports at boot (`netsh interface ipv4 show excludedportrange protocol=tcp`; on 2 Oct 3942-4041), and then `next start -p 4000` fails with EACCES: start the server on a free port (`npx next start -p 3100 -H 127.0.0.1`) and run `PLAYWRIGHT_PORT=3100 npx playwright test`. After `npm ci` brings a new Playwright, run `npx playwright install chromium`. npm 11 skips the postinstall of `@sentry/cli` and `unrs-resolver` (harmless locally). A database reset (`npx supabase@2.109.0 db reset`) rebuilds 0001 to the latest migration.
- **Preview link and test selection (10 Oct, ADR-013):** one dev server per session on a fixed port, started once: `npm run dev -- -p 3200 -H 127.0.0.1` (http://127.0.0.1:3200, or http://127.0.0.1:3200/#footer for the home footer); it follows the checked-out branch and reloads on every edit, so no per-build ports or `.next-*` folders. After a change run `npm run verify` (it ends with the dependency audit; offline `npm run verify:static`) and `npm run test:related` (the specs that cover the changed files, the full suite for anything shared; it uses this checkout's own preview server automatically, found through `.next/dev/lock`); the full suite runs in CI.
- **Gotchas:** Turbopack refuses a symlinked `node_modules`, so build in the main checkout (check out `origin/main` detached to test a baseline, then switch back). `next build` also type-checks `tests/`. `pkill -f "playwright test"` kills your own shell. The cloud container cannot reach spintra.io (egress proxy; do not work around it). Never run multiplayer Playwright against the Vercel preview or production, because it writes to the production database.
- **Evidence techniques that worked:** revert the fix and the new test must fail; compare a flaky test on clean `main` and on the branch; force City dice through `city_match.rng_counter` (`city_derive_dice(seed, counter)` is deterministic).
- **Known flakes:** `multiplayer-loop.spec.ts` "XP earned from a trivia win survives an immediate reconnect" (1 failure in 41 repeats, cause not established); `qa-x15` was a 1-in-8 flake and is fixed in PR #68 (not yet on `main`, so it can still fail in CI until the PR merges; CI's retries cover it); `qa-x24-board-fit` read the City board mid-resize and failed all three CI attempts once (30 Sep), fixed in PR #68. **`tournament-ties.spec.ts` "in a room, the standings show the score difference" (added in #68) failed once in about 17 runs** (the first run after a server start, with a CPU-heavy temporary spec running beside it); it passed in 12 isolated and contended repeats and in 3 more full-group repeats with traces on, so the cause is not established.
