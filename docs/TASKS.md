- `[x]` **Sentry error monitoring** — `@sentry/nextjs` was installed and `sentry.{client,server,edge}.config.ts` existed, but nothing actually loaded them: no `withSentryConfig` wrapper on `next.config.ts`, no `instrumentation.ts` (required for the server/edge configs to ever run on Next.js 15+). Fixed both; confirmed via `npm run build` that the Sentry build plugin is now genuinely active. Gracefully no-ops without `NEXT_PUBLIC_SENTRY_DSN` set, so nothing changes for anyone without a configured DSN. **Requires the user's own setup to actually report anything**: `NEXT_PUBLIC_SENTRY_DSN` (and optionally `SENTRY_ORG`/`SENTRY_PROJECT`/`SENTRY_AUTH_TOKEN` for source maps) in `.env.example`.
- `[x]` **Migration 0047 (fingerprint-based ban evasion prevention)** — found and fixed a self-defeating bug: the `copy_fingerprint_to_ban` trigger looked up the banned user's fingerprint from `room_participants` *after* the kick flow had already deleted that row (both real kick call sites delete before inserting the ban), so `room_bans.fingerprint_hash` would always end up `null`, silently disabling the entire feature. - `[x]` **Migration 0048 (Bingo win verification)** — found and fixed two real bugs in the accompanying client code: (1) the host-side verification query matched the claimer by `username`, which isn't unique in this app (the whole reason `disambiguatedUsernames()` exists elsewhere) — could match the wrong participant's card or silently reject a legitimate win on a name collision; fixed by adding `userId` to the `bingo_win` event and matching on that instead. (2) The event-listener `useEffect`'s dependency array included `isHost`/`bingoWinner`/`bingoCalled` — since `registerEventListener` replays the *entire* event log on every call, this meant every single `bingo_call` event re-triggered the effect, which re-registered and replayed the whole log again, growing `bingoCalled` further, triggering another re-run — an infinite loop that would have crashed/frozen the Bingo activity the moment a host called the first number. Fixed by moving the frequently-changing values into refs (synced via a separate effect, not during render — required by this project's React Compiler lint rules) and restoring the effect to `[registerEventListener]` only, matching every other activity's identical pattern.
- `[x]` **Daily DB backup workflow** (`db-backup.yml`) — reviewed, no code bugs (correct secret handling via GitHub's automatic log masking, reasonable `pg_dump` flags). **Will fail daily until configured**: needs `SUPABASE_DB_URL` and 3-4 AWS secrets (`AWS_BACKUP_ACCESS_KEY_ID`/`AWS_BACKUP_SECRET_ACCESS_KEY`/`AWS_BACKUP_S3_BUCKET`, region optional) set in GitHub repo secrets before it can succeed — this is infrastructure setup only the user can do, not a code gap.

### Critical (1/1) — done, fully re-verified live

Fixed: migration `0036` (RLS on `realtime.messages`, scoped by `is_member_of_room()`) + client change (`private: true` channel config, gated on a new `participantRowReady` flag so a client never subscribes before its own participant row exists — required since Realtime Authorization is cached per-connection at subscribe time).
