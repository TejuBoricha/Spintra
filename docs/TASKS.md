## Session 41: Production Readiness Audit (60 findings, being fixed tier-by-tier)

Full write-up with Description/User impact/Technical impact/Recommended fix/Effort for every item lives in the Session 41 artifact report (see `CHANGELOG_AI.md` Session 41 for the full list); this section tracks fix status only.

### Unplanned, found while the user manually tested this session's fixes
- `[x]` **Lucky Wheel would spin forever, never landing.** A genuine feedback loop: its listener-registration effect (uniquely among 14 activities) depended on `drawWheel`, which itself depends on `wheelSpinning` — every spin transition re-registered the listener, which replayed the still-present `wheel_spinning` event from the new activity-state persistence log, restarting the spin forever. Fixed by reading `wheelEntries`/`drawWheel` via refs instead of effect dependencies. Hazard documented in `ARCHITECTURE.md`'s Pub/Sub section for future activities.
- `[x]` **Room capacity permanently shrank every time someone joined and left.** A disconnected participant's row is kept (`is_online=false`), never deleted, but every capacity check — the DB trigger and 4 separate client-side pre-checks (home, explore, navbar, room-client) — counted every row regardless of online status. Fixed via migration `0026` + matching client-side fixes; verified against the exact room the user hit this in.
- `[x]` **Host election failed in production with `record "new" has no field "settings"`.** Migration `0014`'s `restrict_host_promotion_update()` trigger referenced `rooms.settings`, but migration `0017` (which ran later) dropped that column and never updated the function — broken since 0017 shipped. Fixed via migration `0027`, pushed directly to the live project given real users were affected; verified via `verify-migration.mjs` and a direct `pg_proc.prosrc` check.

### Medium (14/16)
- `[x]` Guess-the-Number secret broadcast to all clients + forgeable win claim. Fixed via migration `0028`: secret and hint-check moved server-side behind two SECURITY DEFINER RPCs (`set_guess_number_secret` host-only, `check_guess_number` room-members-only), backed by a table with no direct SELECT/INSERT/UPDATE policies at all — no client can read the secret back through the API. Verified live (host-only set, RLS-blocked direct read, correct hints, non-member denied).
- `[x]` Room-capacity check TOCTOU race. Fixed via migration `0029`: `pg_advisory_xact_lock` keyed on room code serializes concurrent joins to the same room. Verified live under real concurrency — 10 simultaneous join attempts for a room's single remaining slot, exactly 1 succeeded.
- `[x]` Username edit strips all non-ASCII characters. `room-sidebar.tsx`'s edit input filtered to `a-zA-Z0-9_` only, mangling any accented/CJK/Cyrillic/etc. name. Fixed with a Unicode-aware `\p{L}\p{N}` filter (plus space/`_`/`.`/`'`/`-`) that still blocks control characters and emoji.
- `[x]` Message reports have no rate limit. The existing `unique (message_id, reporter_id)` constraint only stopped re-reporting the same message. Fixed via migration `0030` (10 reports/10min per reporter, same pattern as 0011/0025). Verified live: 11 reports of 11 distinct messages, exactly 10 succeeded.
- `[x]` Overly permissive CSP (`unsafe-inline`/`unsafe-eval`). Dropped `unsafe-eval` entirely (nothing in the app needs it, confirmed via a live production build/run including the WebGL Lucky Wheel — zero violations). `unsafe-inline` on `script-src` could **not** be dropped without Next.js's nonce-based CSP pattern, which requires reading `headers()` in the root layout and forces the whole app out of static rendering — rejected as disproportionate (conflicts with the Critical-tier Explore scalability work). Moved the app's one inline script to a static file (`public/e2e-create-room-bridge.js`) regardless, as a real (if insufficient alone) improvement. User confirmed this trade-off via AskUserQuestion before proceeding. (`unsafe-eval` later made conditional on `NODE_ENV` after it was found to break `next dev`.)
- `[x]` Supabase outage misreported as "room not found." `room-client.tsx`'s `verifyAccess` treated a genuine fetch error (`roomError`, e.g. network failure/outage) identically to `!room` (query succeeded, zero rows — genuinely doesn't exist), both showing "Room Not Found." Separated into a new `"error"` access state ("Couldn't Connect" + Try Again/reload button). Also fixed the outer `catch` block, which previously swallowed any unexpected exception silently (no error state set at all, falling through toward rendering the room UI with incomplete data) — now also surfaces the same "Couldn't Connect" state. Verified live: a genuinely nonexistent room still shows "Room Not Found"; a simulated fetch failure (Playwright route interception) now correctly shows "Couldn't Connect" with a working Try Again button.
- `[x]` No health-check/uptime monitoring. Added `GET /api/health` (`force-dynamic`, never cached) — runs a real, cheapest-possible zero-row query against `rooms` and returns `200 {"status":"ok","database":"reachable"}` or `503 {"status":"error", ...}` if the query fails or env vars are missing. Verified live: `200` against the real production database, `503 not_configured` with env vars unset.
- `[x]` Rate-limit/ban triggers fire with zero observability. Migration `0032` adds `log_moderation_event()`, called from all 5 rejection triggers before their `raise exception` — uses `raise log` (Postgres server log, Supabase Dashboard → Logs → Postgres Logs, filter `MODERATION_EVENT`), not a table write. **A first table-based attempt was caught live logging zero rows, ever** — `raise exception` rolls back the whole transaction including a table INSERT made moments earlier in the same trigger; corrected before committing. Verified live: ban-rejoin and message-report-rate-limit rejections both confirmed still firing correctly after the fix.
- `[x]` Unbounded chat/participant list growth, no virtualization. Participants are already naturally bounded (`max_participants` tops out at 50), so no fix needed there. Chat messages grew unbounded over a long-running session (every incoming realtime message appended forever, each row a Framer-Motion-wrapped DOM node). Added `capMessageHistory()` (`src/lib/utils.ts`), keeping the most recent 500 — applied where messages arrive automatically over time (`addIncomingMessage`); left the "Load older messages" pagination path uncapped since it's a deliberate, self-limiting user action, not automatic growth.
- `[x]` Unbounded `select("*")` on trivia/prompt tables — silent truncation risk. 5 activities (Trivia, Never Have I Ever, Truth or Dare, Word Scramble, Would You Rather) fetched their full question/prompt bank with no `.limit()` — PostgREST silently truncates past its configured row cap, no error, so future content growth could make categories/prompts vanish from the picker without any signal. Added explicit generous limits (`trivia_questions`: 2000; `activity_prompts` per type: 1000) — comfortably above current content volume, so today's behavior is unchanged; only prevents future silent truncation.
- `[x]` Join-validation logic triplicated across 3 pages, no caching layer. Home page, Explore, and the navbar's quick-join dialog each hand-rolled the same room-exists/locked/full/banned/already-a-member checks — and had already drifted apart: navbar's copy was missing the host/existing-member bypass and the ban check entirely, so a banned user or existing member got different (wrong) behavior depending on which UI they used. Extracted to one shared `checkCanJoinRoom()` (`src/lib/room-join-check.ts`), used by all 3, with an 8s in-memory de-dup cache (the room page's own `verifyAccess` re-runs the same check moments after a pre-check already ran). Also fixes the `roomError`/`!room` conflation bug (same class fixed in `room-client.tsx`) in one place instead of three. Verified live: locked-room rejection now correctly fires via the navbar dialog specifically (previously impossible — no such check existed there), toast text confirmed via `[data-sonner-toast]`; unlock-then-retry (past the cache TTL) correctly navigates through.
- `[x]` Realtime connection ceiling vs. Supabase plan tier undocumented. Documented in `ARCHITECTURE.md` §10 ("Realtime Connection Ceiling") — every open room holds one Realtime WebSocket per participant, and Supabase's concurrent-connection limit is plan-tier-dependent and invisible to this codebase. Deliberately doesn't hardcode a specific number (tiers/limits change over time); instructs checking Supabase Dashboard → Usage/Billing before any launch/marketing push.
- `[x]` No CD step in-repo / branch protection unconfirmed. Confirmed both directly: no CD workflow exists (correct — no deploy target chosen yet, nothing to deploy to); `main` had zero branch protection (GitHub API returned 404 "Branch not protected"). User confirmed via AskUserQuestion, then enabled protection requiring `validate`+`db-integration` to pass before merging (no PR-review requirement, `enforce_admins: false` — deliberately low-friction for solo pre-launch dev), force-pushes/deletion blocked. Verified live via the GitHub API afterward.
- `[x]` Room creation missing `authReady` guard (same race class fixed elsewhere). `create-client.tsx`'s `currentUser.id` starts as a local random id, only overwritten with the real `auth.uid()` once sign-in resolves; clicking "Create Room" fast enough persisted `host_id` as the stale local id (RLS on `rooms` INSERT is wide open, so nothing rejected it) — the creator would then fail to be recognized as their own room's host once `currentUser` updated. Added `authReady` gating the button, plus `authReadyRef`/`currentUserRef` mirrors so `handleCreate` itself waits for and reads the latest values regardless of entry point (the E2E test bridge calls `handleCreate` directly, bypassing the button's disabled state). Verified live: raced a click via the unguarded decoy button as fast as possible — persisted `host_id` is a real UUID (`auth.uid()`), not the stale 8-char local id format.
- `[ ]` No `aria-live` region for room notifications / participant join-leave / game-state changes.
- `[ ]` Trivia correct/incorrect feedback is color-only.
